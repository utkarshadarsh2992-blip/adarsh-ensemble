# Controller wire contract v2 — source of truth

All documents are secret-free. No chat/prompt or executable code. HTTPS Supabase project URL is fixed to `https://yepupldfjtikalfzehvl.supabase.co`.

## Config schema

`{schema_version:1, providers:{groq:{base_url:string},openrouter:{base_url:string},gemini:{base_url:string},nvidia:{base_url:string},cloudflare:{base_url:string}}, models:[{label:string,provider:string,model:string,enabled:boolean,extra:object}], routes:{[routeKey]:string[]}, quality:{truthLevel?:'strict'|'balanced'|'creative',factCheck?:'off'|'auto'|'always',builtInWebSearch?:boolean,audit?:boolean,ground?:boolean,research?:boolean,review?:boolean,debate?:boolean}, limits:{[provider]:{daily_tokens?:number,daily_requests?:number}}}`.

Provider names fixed to existing 5. Only same exact provider HTTPS host allowed: Groq `api.groq.com`, OpenRouter `openrouter.ai`, Gemini `generativelanguage.googleapis.com`, NVIDIA `integrate.api.nvidia.com`, Cloudflare `api.cloudflare.com`. URLs reject userinfo/port/query/hash/traversal. Cloudflare requires exactly one literal `/accounts/{CLOUDFLARE_ACCOUNT_ID}/` path placeholder; account IDs and API keys stay local. URL is provider base URL, never full `/chat/completions`. No arbitrary headers. Model list <=100 unique labels; IDs <=200 chars. Model extras whitelist only `reasoning_effort` low/medium/high and `reasoning_format` hidden/raw/parsed; no tools/credentials/custom JSON. Missing route uses bundled role chain resolved to current registry. Max route chain 10 unique enabled models. Each role route must cover Groq/OpenRouter/Gemini with first fallback provider different from primary, matching `config.check_chains()`/`mode_plans.validate()`; The Standard council plan has role routes, but the actual direct Standard chat remains Groq-only. Its selected models come from Groq entries in `utility:quick`; `mode:standard:*` does not turn direct chat into a multi-provider council. No synthetic `standard:single` route exists. Partial route keys are exact names generated in `src/default-routes.json`: `mode:<standard|verified|physics|math|business|coding>:<architect|theorist|empiricist|specialist|pattern|skeptic|debater|judge|method|evidence|refiner|verifier|falsifier1|falsifier2|falsifier3>` and `utility:<quick|auditor|master_writer|master_auditor|classifier|stripper|verifier|judge|synthesizer|guard_llm>`. A missing route follows its exact bundled chain. Effective route references for a model are `config.routes[key]` when present, otherwise the exact chain from `src/default-routes.json`. An absent/disabled model may not remain in any effective route. This preserves a safe model-removal path: route all bundled references to supported replacements first, then remove the old label. The effective plans must still satisfy all bundled chain invariants; reject the whole config, retain the last-known-good config, and report actionable route labels on failure.

Quality overrides are partial; omitted property means keep existing local app default. Limits are display-only estimates across observed devices; they do not change provider quota or claim official balance.

## controller-admin (POST, verified Auth Bearer + server allowlist on every action)

- `{action:'state'}` -> `{ok:true,revision:number,config:Config,devices:[{id,name,last_seen,revoked_at,config_revision,applied_revision}],usage:[{device_id,day_utc,report,updated_at}],history:[{revision,created_at,actor_id,reason}]}` bounded to 30 devices, 14 days/<=420 snapshots and 30 revisions; return `next_cursor` where required, accepted as `cursor` on the next state request. PWA shows explicit partial totals until Load more completes; merges are deduplicated and revision-protected.
- `{action:'save',expected_revision:number,config:Config,reason:string}` -> `{ok:true,revision:number}`; optimistic conflict -> HTTP 409. Validate whole effective configuration. Store revision plus audit transactionally.
- `{action:'rollback',expected_revision:number,target_revision:number}` -> new validated revision copied from old config; no data rollback.
- `{action:'pair_code',name:string}` -> `{ok:true,code:string,expires_at:string}` cryptographically random one-time code, >=12 chars and <=10 minutes. Database stores hash only. Name <=60.
- `{action:'revoke',device_id:string}` -> revoke device token; preserve usage/history.

## controller-device (verify_jwt=false; its own one-time pairing/device-token authentication)

- `{action:'pair',code:string,name:string}` unauthenticated one-time pairing exchange -> `{ok:true,device_id:string,device_token:string,revision:number,config:Config}`. Return 256-bit random token once; store only hash. Consume pairing code atomically; expiry/used codes fail. Do not set admin rights.
- Bearer device token + `{action:'sync',config_revision:number,app_version:string,reports?:Report[]}` -> `{ok:true,revision:number,config:Config}`. Verify device-token hash and not revoked; no chat, prompts, provider keys. Max 14 report days (current + up to 13 prior UTC days) and request <=256 KiB. `config_revision` acknowledges only validated active config; 0 means bundled/unacknowledged, mapped to nullable `applied_revision`. Existing `config_revision` on devices means last sent revision; never label it applied. Absolute upsert per device/day; repeated retry is idempotent, stale counters cannot lower totals.

`Report` is the sanitized `health.report()` shape: `day_utc,totals:{req,tok},providers:[{id,name,set,req,tok,keys:[{slot,set,state,cool_s,req,tok,models:[{model,label,req,tok,req_limit,tok_limit,frac,out_s,cool_s,rpm,tpm,min_req,min_tok}]}]}],features:{[known feature]:count},days:[{day,req,tok,by:{[provider]:count}}],truth:{answers,ok,shak,galat},standard:{state,left},margin,reserve,reset_in_s`. Strip unknown fields; bound numbers/lengths and provider/slot IDs. Historical `standard.state` may be `unknown` to avoid inventing a live quota. Older days can have aggregate provider totals only; never fabricate old per-model data.

No secret is returned by `state`; all responses `Cache-Control: no-store`. Service worker caches application shell only; never Auth sessions, reports, pair codes or API responses. Supabase Auth sign-in is email OTP with `shouldCreateUser:false`; no public signup or preview bypass. A verified Auth UUID is in the server allowlist before admin access.
